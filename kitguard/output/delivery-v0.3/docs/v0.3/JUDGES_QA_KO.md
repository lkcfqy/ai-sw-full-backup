# KitGuard v0.3 심사 질의응답 보충안

작성일: 2026-09-26. 팀 내부 리허설용이며, 공식 제출본이 아닙니다. 아래 수치는 **v0.3 개발 28장**, 완료 후 독립 재계산한 **새 평가 64장**, 명시적으로 구분한 **v0.2 과거 평가**입니다. 새 64장은 C59/W0/U5/E0이며 사전에 정한 연구용 채택 조건을 충족했습니다. 현장 효과나 공식 대회 평가는 별도입니다.

## 1. KitGuard가 해결하려는 문제는 무엇입니까?

“주문이 바뀌었는데 이전 사진이나 이전 검사 결과로 출고를 판단하는 문제를 줄이려 합니다. KitGuard는 현재 주문, 사진, 참고 자료와 검사 결과를 같은 버전으로 묶습니다. 수량 차이는 수정 작업으로, 불확실성은 재촬영이나 사람 확인으로 연결하고, 완료 전에는 사용자의 실물 확인을 요구합니다.”

## 2. 사진에 숫자를 답하는 챗봇과 무엇이 다릅니까?

“모델은 물체의 종류와 위치를 제안하고, 프로그램이 목록을 세어 현재 주문과 비교합니다. 새 사진이나 주문 변경이 생기면 이전 검사로 완료할 수 없도록 상태를 관리합니다. 저희가 구현한 핵심은 모델의 답을 사진 근거, 보완 요청, 버전 검사, 사용자 확인과 연결하는 업무 흐름입니다. 새로운 기초모델이나 전 세계 최초의 부품 검수라고 주장하지는 않습니다.”

## 3. 같은 모델을 세 번 부르면 독립된 전문가 세 명과 같습니까?

“아닙니다. 첫 번째는 원본 방향의 물체 목록, 두 번째는 90도 회전 영상의 목록을 만듭니다. 두 목록이 명확하게 일치하고 너트나 와셔 후보가 있을 때만 세 번째로 전체 사진과 해당 위치의 확대 영상을 함께 확인합니다. 같은 모델과 같은 장면을 사용하므로 오류가 함께 반복될 수 있습니다. 저희는 이를 독립 전문가 투표가 아니라, 서로 다른 관찰 형식에서 모순을 찾는 절차로 설명합니다.”

## 4. 정답 수량을 알려 주고 모델이 맞춰 답하게 한 것은 아닙니까?

“관찰 프롬프트에는 주문 목표 수량과 데이터 정답을 넣지 않습니다. 모델은 물체별 종류와 위치를 출력하고, 그 뒤에 프로그램이 수량을 계산해 주문과 비교합니다. 세 번째 확인에도 앞선 분류나 수량을 전달하지 않고 위치 ID와 좌표만 제공합니다. 이번 평가에서는 참고 이미지와 과거 보완 문맥도 사용하지 않았습니다. 이 설명은 입력 경로의 분리를 뜻하며, 모델의 사전학습 지식까지 통제했다는 뜻은 아닙니다.”

## 5. 확인 결과가 충돌하면 올바른 숫자로 고쳐 줍니까?

“자동으로 숫자를 고치지 않습니다. 두 방향의 수량이 다르거나, 확대 확인에서 분류·독립 물체 여부·구멍 형태가 확인되지 않으면 관련 종류를 ‘미확인’으로 처리합니다. 프로그램이 주문에 맞는 숫자를 선택하거나 평균을 내지 않습니다. 특히 와셔는 모델 응답에서 관통 구멍이 확인되어야 통과하지만, 그 응답 자체도 모델의 추정이므로 실제 구멍의 객관적 증명은 아닙니다.”

## 6. 개발 결과에서 무엇이 좋아졌고, 무엇을 잃었습니까?

“완료된 28장 개발 실행에서 같은 실행의 첫 관찰은 25장 정답, 3장 오답을 모두 확정적으로 답했습니다. 최종 후보는 24장을 올바르게 답하고 4장을 보류했으며, 잘못 확정한 답과 실행 오류는 각각 0장이었습니다. 기존 오답 3장을 모두 보류했지만, 맞았던 1장도 추가 확인 대상으로 돌렸습니다. 따라서 단순 정확도가 높아졌다고 말하기보다, 답변 범위와 시간을 지불하고 잘못된 확정 답을 줄인 개발 결과라고 설명합니다.”

| 완료된 v0.3 개발 실행 | C: 정확·실행 가능 | W: 오답·실행 가능 | U: 보류 | E: 실행 오류 |
| --- | ---: | ---: | ---: | ---: |
| 같은 실행의 실제 첫 관찰 | 25/28 | 3/28 | 0/28 | 0/28 |
| 최종 후보 전체 절차 | 24/28 | 0/28 | 4/28 | 0/28 |

첫 관찰과 최종 결과는 **같은 28장의 짝지은 비교**입니다. 56장의 독립 표본이 아니며, 첫 관찰을 별도로 실행한 전체 지연시간은 없습니다. 이 자료는 이미 개발에 사용한 이미지이므로 새 환경 일반화의 증거로 쓰지 않습니다.

## 7. 전부 거절하면 오류가 0이 됩니다. 평가에서 어떻게 막습니까?

“정확하고 실행 가능한 답을 C, 잘못된 실행 가능한 답을 W, 보류를 U, 실행 오류를 E로 나누고 모든 사진을 분모에 남깁니다. 개발 단계는 LOCO 16장 중 C가 최소 13장, Screws 12장 중 최소 10장이어야 하며, 각 그룹의 W와 E는 0이어야 합니다. 실제로는 각각 C 14장과 10장으로 통과했습니다. 새 평가도 그룹별 최소 답변 수와 지연시간을 미리 정했으므로, 많이 거절하거나 실패 사례를 빼서 통과할 수 없습니다.”

“또한 확정 답 중 오류율은 W/(C+W), 전체 사진 대비 오류는 W/N으로 구분합니다. 이번 개발 후보는 각각 0/24와 0/28입니다. 분모가 없는 항목은 0%로 표시하지 않습니다.”

## 8. ‘잘못 답했다’와 ‘잘못 출고했다’는 같은 의미입니까?

“다릅니다. 틀린 관찰은 잘못된 보충 지시를 만들 수도 있고, 잘못된 주문을 수량 일치 상태로 만들 수도 있습니다. 그래서 잘못된 확정 답과 잘못된 준비 완료 판정을 따로 계산합니다. 각 종류 0~3개, 총 1~12개인 255개 주문 조합을 관찰 이후에 비교하고, 그중 하나라도 잘못 일치하는 사진이 있는지 봅니다. 사진 하나에서 파생한 255개 주문을 255개의 독립 시험으로 세지는 않습니다.”

“28장 개발에서는 첫 관찰의 3장에 이런 잘못된 일치 가능성이 있었고 최종 후보에서는 0장이었습니다. 이는 프로그램의 주문 비교 실험이며, 실제 물품이 잘못 출고되었다는 뜻은 아닙니다. 제품에서도 수량 일치 후 사용자의 확인이 있어야 완료됩니다.”

## 9. 더 빠른 OWLv2나 Grounding DINO를 쓰지 않은 이유는 무엇입니까?

“다른 구조의 검출기도 실제로 시험했습니다. 같은 개발 28장에서 사전에 정한 질문·임계값·중복 제거 규칙으로 네 종류의 전체 수량이 맞은 이미지는 OWLv2가 0장, Grounding DINO Tiny가 1장이었습니다. 빠르지만 작은 금속 부품의 누락, 잘못된 종류, 큰 오검출 박스가 있어 현재 판단 경로에는 넣지 않았습니다. 특정 사진에서 잘 잡힌 부품만 골라 다른 모델의 숫자를 고치지도 않았습니다.”

“이 결과는 이번 공개 가중치와 고정된 제로샷 설정에 한정합니다. 해당 모델 계열 전체가 부적합하다는 결론은 아닙니다. 두 검출기의 원시 박스·점수·실패와 CPU 실행 기록을 모두 보존했습니다.”

## 10. 공개 이미지에서 잘하면 실제 공장에서도 잘합니까?

“공개 자료로 확인한 것은 지정한 영상과 분류 범위에서의 동작입니다. 새 평가에서는 이전에 사용한 원본과 겹치지 않도록 출처 단위로 나눴지만, 그것이 다른 공장이나 독립 촬영 회차를 뜻하지는 않습니다. Screws 일부는 저자가 표기한 물체가 온전히 들어오는 원래 픽셀의 안전한 사각 영역을 사용하므로, 전체 원본 이미지 성능과도 구분합니다. 기초모델이 이 공개 자료를 사전학습에서 보았는지는 알 수 없습니다.”

“현재 정량 평가에는 각도 브래킷의 양성 사례가 없고, Screws 그룹에는 와셔 양성도 없습니다. 따라서 네 종류 모두를 검증했다고 말하지 않습니다. 모델이 반환한 점은 추정 위치이며, 정밀 위치 정답이나 나사 규격·재질·SKU 판별을 대신하지 않습니다.”

## 11. 40초 이상 걸리면 실용성이 있습니까?

“완료된 개발 28장에서 전체 절차의 중위시간은 43.50초, 최대는 53.03초였습니다. 그룹별 중위시간은 LOCO 47.26초, Screws 21.38초입니다. 원본·회전 관찰은 각각 최대 900 출력 토큰, 조건부 확대 확인은 최대 1,800 토큰을 사용합니다. 이 시간에는 업로드 정규화와 실제 모델 실행이 들어가며 첫 실행도 제외하지 않았습니다.”

“지금은 고속 생산라인보다 소량 부품 준비를 사람이 확인하는 보조 작업을 목표로 합니다. 추가 확인의 비용은 분명합니다. 사람의 작업 시간을 포함한 편익을 측정하기 전에는 속도나 인건비 절감을 주장하지 않으며, 추가 호출이 실제 오류를 줄이지 못하면 더 단순한 모드를 유지한다는 채택 기준을 세웠습니다.”

## 12. 과거의 46/48 결과와 이번 24/28을 직접 비교해도 됩니까?

“안 됩니다. v0.2의 46/48은 과거에 고정한 LOCO 평가 48장에 대한 단일 공간 목록 결과이며, 두 오답 중 한 장은 정상 주문에서 잘못 준비 완료로 판정되었습니다. 이번 24/28은 다른 목적의 개발 자료에서 추가 확인을 포함한 C, 즉 정확하고 실행 가능한 답의 수입니다. 데이터, 단계와 답변 정책이 달라 두 비율의 차이를 성능 향상이나 하락으로 계산하지 않습니다.”

“새 64장에서는 미리 고정한 동일 실행의 첫 관찰과 최종 결과를 비교했습니다. 첫 관찰 C62/W2에서 최종 C59/W0/U5로 바뀌었습니다. 틀린 확정 답 2개를 보류하는 대신 맞았던 3개도 보류했으며, 이를 단순 정확도 향상이라고 부르지 않습니다. 전체64장과 모든 보류 결과를 공개합니다.”

## 13. 실제 사용자가 물건을 보충한 뒤 효과가 있는지 시험했습니까?

“현재 완료된 근거는 실제 로컬 모델 실행, 공개 사진 평가, 버전·오류 처리 시험과 브라우저 흐름 검증입니다. 실제 사람이 같은 업무를 수행한 대조 실험과 보충 전후의 새 실물 촬영 실험은 아직 결과가 없습니다. 공개 사진을 다시 올린 시연을 실제 보충 성공으로 설명하지 않습니다. 다음 검증은 사람이 직접 세는 기준과 함께 누락 탐지, 추가 촬영 횟수, 최종 오류, 전체 소요시간을 측정하는 것입니다.”

## 14. SHA-256이 있으면 기록을 믿을 수 있다는 뜻입니까?

“해시는 보관한 코드와 이미지가 특정 시점의 파일과 같은지 검사하는 도구입니다. 다른 사진으로 바뀌었거나 실행 중 코드가 달라진 경우를 추적하는 데 사용합니다. 그러나 누가 촬영했는지, 실제 현장인지, 기록 작성자가 파일과 해시를 함께 바꿨는지는 해시만으로 증명할 수 없습니다. 저희 기록은 재계산 가능한 추적 근거이지, 공인 전자서명이나 현장 진위 인증이 아닙니다.”

“28장 개발 실행은 보관된 코드, 두 방향 입력 56개와 필요한 확대 영역을 재구성해 기록과 일치하는지 확인했습니다. 애플리케이션이 보존하는 확대 자료는 좌표와 해시 등 메타데이터이며, 임시 확대 PNG가 모두 영구 보관된다고 설명하지 않습니다.”

## 15. 보유한 Mac에서 실제로 실행했습니까? 다른 컴퓨터도 검증했습니까?

“실제 모델 평가는 M5 Pro, 통합 메모리 64GB의 Mac에서 MLX로 실행했습니다. 고정한 Qwen3.6-27B 4비트 공개 가중치를 사용하며, 정상 관찰 경로는 클라우드 모델 API로 사진을 보내지 않습니다. 모델 파일과 설정의 출처·리비전·해시를 보관했습니다. OWLv2와 Grounding DINO 비교만 명시적으로 CPU와 최대 4개 계산 스레드를 사용했습니다.”

“별도로 보유한 RTX 3080 PC의 Windows 실행 성능은 검증하지 않았습니다. 현재의 재현 가능 범위는 실제 시험한 Mac 환경이며, 운영체제나 하드웨어가 달라지면 설치·메모리·지연시간을 다시 확인해야 합니다.”

## 16. 팀이 직접 만든 부분과 공개 도구를 어떻게 구분합니까?

“공개 모델과 MLX·웹 프레임워크를 기반으로, 주문 버전 관리, 사진 증거와 검사 결과의 결합, 결정 규칙, 보완 요청, 동일 이미지 처리, 확인 절차, 감사 화면과 평가 도구를 구현했습니다. AI 코딩 도구의 도움도 사용했고 출처와 변경 기록을 남겼습니다. 모델 성능은 실제 모델 호출로, 상태 제약은 별도의 CPU·API 시험으로 검증합니다. 모의 모델을 쓴 소프트웨어 시험 횟수를 인식 성능 표본에 더하지 않습니다.”

## 17. 새 64장 결과와 채택 판단을 한 문장으로 설명한다면?

“내부에서 사전 동결한 64장 중 59장에 정확하고 실행 가능한 답을 제공하고 5장은 보완으로 넘겼으며, 잘못 확정한 답과 실행 오류는 0장이었습니다. 실제 첫 관찰의 오답 2개를 차단했지만, 정답 3개도 추가 확인 대상으로 보냈습니다. 이 범위와 비용을 포함해 미리 정한 연구용 채택 조건을 충족했습니다.”

| 완료된 새 평가 | C | W | U | E | 중위시간 |
| --- | ---: | ---: | ---: | ---: | ---: |
| LOCO 정상16장 |16|0|0|0|47.27초|
| LOCO 수량 이상16장 |15|0|1|0|45.03초|
| Screws32장 |28|0|4|0|22.40초|
| 전체64장 |59|0|5|0|40.58초|

확정 답 중 오류는 0/59이고, 전체 사진 중 올바른 답변 범위는 59/64(92.19%)입니다. 명목 주문 아래 이상 사진의 오류 준비 완료 0/16, 고정 교란 주문 0/64, 255개 주문 조합 중 어느 하나라도 잘못 준비 완료가 되는 사진 0/64였습니다. 첫 관찰은 마지막 지표에서 2/64였습니다. 0이라는 관측 결과를 현장 위험이 없다는 뜻으로 사용하지 않습니다.

이 64장에서는 방향 비교가 맞았던 3장을 보류했고, 신원 확인이 잘못된 2장을 보류했습니다. 개발 자료에서의 역할은 달랐으므로, 이번 결과만 보고 회전 단계를 사후 삭제하지 않습니다. LOCO 055의 원래 목록은 수량이 맞았지만 두 번째 방향과 달라 최종 bolt가 미확인입니다. 최종 counts_exact와 C는 모두 59/64이며, 원래 목록을 최종 답으로 세지 않습니다.

연구 실행 기본은 시작 스크립트의 환경변수로 spatial_guarded를 선택합니다. 핵심 클래스의 호환 기본 spatial_inventory와 구분하고 실행 모드를 기록합니다. 이 64장은 이제 평가에 사용했으므로 향후 재실행은 새로운 미사용 평가가 아닌 회귀 검증입니다.

사전 동결은 로컬 파일과 SHA 기록으로 확인한 내부 절차입니다. 외부 등록 기관에 공개 등록했다는 주장은 아닙니다. API의 decision=`correct`는 인식 정답이라는 뜻이 아니라 ‘수량 조정 필요’이며, `ready`는 ‘수량 일치, 사람 확인 필요’입니다.
