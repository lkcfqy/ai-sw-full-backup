## 经反例验证并修复的问题

| 风险 | 修复后行为与回归证据 |
| --- | --- |
| 先登记，然后从另一个工单查看同一图片的 AI 结果 | 自述现场批次在冻结、人工开始、AI 开始及成功结束时重新检查已知同 SHA 暴露；各路径均拒绝，失败/放弃仍可记录 |
| 看见错误 `ready` 后选择失败、放弃或关闭，从主结果中隐藏错误 | 终态保留实际窗口内事件与 check；主终态继续显示失败/放弃，`returned_checks` 另列实际已返回的错误与错误 ready |
| 推理正在运行时提前关闭，晚到错误结果永远落不到报告 | 存在实际 `active_inspection` 时失败、放弃和关闭返回 409；结果真正提交后再结束时保留错误记录。三个并发反例均通过 |
| 工程替身被正常完成路径拒绝，却借失败路径混入真实模型诊断计数 | 所有原 check 保留，但非工程批次只有 `backend=mlx` 且匹配冻结身份的返回可计分；替身保留为不可计分来源 |
| 原有公开图库像素手工重传后被标为自采现场 | 与已存 `demo_source` 图片相同的 SHA 不能登记为自述现场，和是否已做过推理无关 |
| 运行中记录器源码变化，仍提交成功结果 | 成功结束再次核对冻结源码 SHA；改变时可记录失败，不可记正常完成 |
| 重启后用另一进程的单调时钟继续计时 | 原进行中试次保留为 `interrupted`，耗时 `null`，已有 check 和错误计数继续保留 |
| 尚无开始试次被显示成有观测结果 | 保留全部预定槽位和未开始数量；正确率为 `null`，不生成伪造的成功率 |

## 仍需保留的结论边界

- “自述现场”仍是操作者声明。系统可以拒绝已经知道的公开图与重复像素，无法证明未见过的上传文件真的在现场拍摄，也无法检测另一软件中事先见过答案。
- 两次数量输入一致不证明由两个人独立计数。同浏览器隐藏真值不能叫盲测；人工先、AI 后存在记忆和顺序效应。
- 每个案例只覆盖一个固定图片/物体状态。计时从登记和拍照之后开始，不是完整实体作业时间；没有连续补件实验或因果效率提升证据。
- 超时后被现有订单接口丢弃、从未形成已提交 check 的后台生成，不算已返回有效 check。错误/超时尝试仍进入失败与事件记录。
- 已知返回错误在额外诊断列展示；主终态分母始终保留失败、放弃、中断和未开始。阅读时不能只取成功试次的耗时或只取可回答样本宣称总体表现。
- 本次只执行工程测试。真实现场效果仍需实际采集后生成，不能用本次工程记录填充现场成绩。

## 独立导出复算工具

新增标准库工具 `scripts/verify_study_export.py`，完全不导入或复用应用的评分实现。仅支持当前 schema 1 的完整已关闭 JSON；复算盐化真值承诺、协议散列、案例与 check 绑定、人工先 AI 后的时间顺序、事件与 check 对应、全计划分母、各终态、空耗时规则和所有已返回错误。它只读输入，可输出独立 JSON 收据；有效退出 0，无效退出 1，收据写入失败退出 2，已有收据不会被覆盖。

真实浏览器工程导出 `test-results/browser/field-study-v04/engineering-study-export.json` 已通过：6 个计划案例、9 个已开始试次；人工 C3/W1/A1/N1，AI C1/W1/U1/E1/N2，分母各为 6。这是浏览器工程夹具的真实运行记录，不是真人或真实模型效果。复算收据为 `test-results/audit/v04-study-export-verification.json`。

`tests/test_study_export_verifier.py` 的 **40 项测试全部通过**，含已返回错误保留在失败状态下的正例，以及真值/nonce/协议/订单或照片绑定/来源提升/时间/漏 check/计划分母/错误计数等篡改负例。Ruff 通过。

工具限制明确写入每份收据：不验证照片字节（另由照片 ZIP 校验器处理）、不验证身份签名，不独立重测时长；一份整体伪造且内部一致的无签名文档，或在所有记录段中一致删去的事件，无法仅靠此 JSON 检出。
