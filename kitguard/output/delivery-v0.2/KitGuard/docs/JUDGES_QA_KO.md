# KitGuard 심사 질의응답 준비본

작성일: 2026-09-26 · 팀 해피 · 국립창원대학교 인공지능융합공학과

현재 구현과 증거 범위에 맞춘 답변입니다. 진행 중인 평가의 일부 수치는 사용하지 않았습니다. 최종 발표 수치는 완료된 평가 보고서와 일치시켜야 하며, 이 문서는 참가 자격이나 제출 승인을 의미하지 않습니다.

## 1. KitGuard는 무엇을 해결하나요?

소량 부품 세트가 **현재 주문의 종류별 수량과 일치하는지** 확인하는 보조 도구입니다. 주문 변경, 새 사진, 불확실한 관찰을 작업 상태와 연결하여 다음 행동을 안내하고 검사 근거를 남깁니다. 현재 범위는 볼트·나사류, 너트, 와셔, 브래킷의 네 가지 큰 분류이며, 주문은 종류별 0~3개, 전체 1~12개입니다. 규격·길이·재질을 구별하는 정밀 SKU 검사나 공장 출하 보증을 제공하지 않습니다.

## 2. 단순 이미지 분류기에 Agent라는 이름을 붙인 것 아닌가요?

이미지 관찰은 한 단계입니다. 시스템은 자연어 주문 변경 제안을 사람이 승인한 뒤 현재 주문으로 저장하고, 사진 관찰과 규칙 비교 결과에 따라 재촬영·물체 분리·수량 수정·사람 확인을 선택합니다. 새로운 증거가 들어오면 이전 결과의 유효성을 다시 검사하고, 작업 이력과 근거를 ZIP으로 내보냅니다. **목표, 상태, 도구 실행, 피드백이 연결된 제한적 업무 Agent**라는 의미이며, LLM이 임의의 도구를 자유롭게 실행하는 구조는 아닙니다.

## 3. 이미 있는 kitting 제품과 무엇이 다른가요? 세계 최초인가요?

세계 최초라고 주장하지 않습니다. [Tulip의 Kitting](https://support.tulip.co/docs/kitting), [Roboflow의 Kitting Verification](https://roboflow.com/ai/kitting-verification) 등에서 부품 확인과 작업 추적을 이미 다룹니다. 이번 구현의 기여는 작은 로컬 장비에서 주문 변경과 사진 버전을 묶고, 관찰·비교·보완 요청·완료 조건·감사 자료를 하나의 실행 가능한 흐름으로 구성한 것입니다. 기존 상용 제품보다 정확하거나 저렴하다는 비교 실험은 아직 없습니다.

## 4. 왜 27B 모델을 Mac에서 로컬로 실행하나요?

현재 장비인 MacBook Pro M5 Pro 64GB에서 실행을 확인했고, 개발용 사례를 비교한 뒤 Qwen3.6-27B의 MLX 4-bit 변환본을 선택했습니다. 사진을 외부 추론 API로 보내지 않고 실행할 수 있으며, 모델과 실행 설정을 고정하여 재현할 수 있습니다. 다만 모델 크기가 정확성을 보장하지 않습니다. 기록된 약 19GB의 MLX 최고 메모리 값은 **MLX가 보고한 값**이며 시스템 전체 메모리 사용량이나 여유 RAM을 의미하지 않습니다. RTX 3080에서 이 MLX 파일을 실행한 결과도 아닙니다.

## 5. 모델이 정답 수량을 보고 거기에 맞춰 답하는 것은 아닌가요?

현재 시각 관찰 프롬프트에는 주문의 목표 수량을 넣지 않습니다. 모델은 사진에 보이는 물체를 관찰하고, 별도 프로그램이 승인된 주문 수량과 비교합니다. 주문 수량을 바꾸어도 관찰 입력이 같게 유지되는지 CPU 기반 검사를 수행했습니다. 이 구조는 목표 수량 유출을 줄이지만, 공개 사진을 모델이 사전학습에서 보았는지까지 증명하지는 못합니다.

## 6. 화면의 점과 좌표가 검증된 물체 위치인가요?

아닙니다. 선택한 관찰 방식은 모델이 물체마다 큰 분류와 추정 중심 좌표를 출력하고, 프로그램이 항목 수를 세는 방식입니다. 점은 모델이 무엇을 셌는지 검토하는 데 도움을 주지만 **정답 위치, 추적 ID, 실제 부품 존재의 증명**이 아닙니다. 누락·중복·오분류가 가능하며, 현재 공개 데이터 평가에 위치 정확도 점수는 포함하지 않습니다.

## 7. 모델이 틀렸을 때 자동으로 출하를 허용하나요?

수량이 맞는다는 모델 기반 판정만으로 작업을 완료하지 않습니다. 현재 주문 버전, 현재 사진, 유효한 검사 결과를 확인하고 마지막에는 사용자의 실물 확인을 요구합니다. 구조가 잘못된 응답이나 불명확한 수량을 0으로 바꾸어 통과시키지 않습니다. 다만 확신 있게 틀린 관찰은 여전히 위험하므로 이 구현을 안전 인증이나 무인 출하 시스템으로 제시하지 않습니다.

## 8. 보완 촬영으로 실제 오류가 해결된 것을 검증했나요?

새 사진이 이전 판정을 무효화하는지, 피드백이 올바른 주문과 사진에 연결되는지, 오래된 결과로 완료할 수 없는지는 소프트웨어에서 검증했습니다. 공개 실사진도 실제 로컬 모델로 관찰했습니다. 그러나 **같은 실물 세트에 부품을 추가·제거하고 연속 촬영한 현장 검증은 아직 없습니다.** 서로 다른 공개 사진을 올린 것은 실제 물리적 수정의 증거가 아닙니다. 실물 확인이 필요한 완료 버튼은 공개 사진 데모에서 대신 눌러 증명하지 않습니다.

## 9. 테스트가 많이 통과했다는 것이 인식 정확도인가요?

아닙니다. 엔지니어링 테스트는 주문 변경, 입력 검증, 상태 전이, 오래된 결과 차단, 증거 묶음 등의 프로그램 동작을 확인합니다. 일부는 합성 사진과 고정된 테스트 관찰 결과를 사용합니다. 모델 인식 성능은 별도의 공개 실사진 평가로 계산하며, 자연어 주문 이해 평가도 별도입니다. 발표에서는 세 분모를 합치지 않습니다.

## 10. 공개 이미지의 정답은 어떻게 만들었나요?

MVTec LOCO AD의 `screw_bag` 정상 구성은 긴 나사 1개, 짧은 나사 1개, 너트 2개, 와셔 2개입니다. 프로젝트의 큰 분류로는 나사류 2·너트 2·와셔 2가 됩니다. 수량 이상 사진은 저자의 단일 수량 결함 이름과 마스크 값으로 수량을 명확히 결정할 수 있는 경우만 사용했습니다. 혼합 결함·손상·길이 교체 등은 추측해 넣지 않았습니다. 나사류를 합쳤으므로 긴 나사와 짧은 나사의 교체 검사를 수행한 것으로 해석하면 안 됩니다.

## 11. 평가가 쉬운 사진을 고른 것 아닌가요? 공개 데이터 오염 가능성은요?

후보 포함 조건, 고정 seed, 이미지 SHA에 따른 순서와 분할을 저장했습니다. 개발용 16장과 별도 48장 평가 집합을 사용하며, 저자 원래 test 중 8장을 개발용으로 다시 나눈 사실도 공개합니다. 정상 수량은 일정하므로 정상과 수량 이상을 나누어 보고하고, 항상 정상 수량만 답하는 기준도 구분합니다. 다만 공개 이미지의 **사전학습 포함 여부는 확인할 수 없습니다.** 이 분할은 팀의 개발 과정에서 결과를 보지 않고 남긴 집합이지, 기반 모델이 한 번도 보지 않은 사진이라는 보장은 아닙니다.

## 12. 네 종류 모두 실제 사진으로 검증했나요?

아닙니다. 현재 LOCO 자료는 나사류·너트·와셔를 포함하며 브래킷 양성 사진은 없습니다. Screws 자료는 실제 여러 나사·너트 사진이지만 현재 주문의 종류별 최대 3개 범위를 초과하므로 별도의 계수 스트레스 사례로 다룹니다. 브래킷, 다른 배경·조명·가림, 같은 실물의 수정 전후 사진을 추가 수집한 뒤 별도 검증해야 합니다.

## 13. 공개 데이터와 모델을 대회나 사업에 마음대로 쓸 수 있나요?

아닙니다. Qwen 모델의 보존된 원본 라이선스는 Apache-2.0이며, MVTec LOCO AD와 Screws는 **CC BY-NC-SA 4.0**입니다. 데이터 출처·저작자·비상업 조건·동일조건 공유 등의 조건을 보존합니다. 무료 다운로드가 상업 사용 허가를 뜻하지 않으며, 상금 대회·외부 배포·후속 사업에 대한 구체적인 허용 범위를 이 문서가 대신 승인하지 않습니다. 제출 자료에는 공개 사진 출처를 표시하고, 사용 목적이 달라지면 권리자 조건을 확인하거나 자체 자료로 교체해야 합니다.

## 14. AI가 코드를 만들었다면 팀이 직접 한 것은 무엇인가요?

Codex를 코드 생성·수정·테스트·문서 작성·교차 점검에 사용했습니다. 모든 코드를 팀원이 직접 한 줄씩 작성했다고 주장하지 않습니다. 공개 기반 모델도 새로 학습하거나 미세조정하지 않았습니다. 팀이 설명하고 책임져야 할 신규 구현은 주문과 증거의 버전 제약, 자연어 수량 검증, 관찰 결과의 구조 검증과 프로그램 계수, 보완 요청 및 상태 전이, 사용자 확인, 감사 ZIP, 고정 평가와 인터페이스입니다. 공식 규칙에 따라 도구와 기존 자산, 신규 개발분을 출처·AI 활용 신고서에 공개할 준비를 하고 있습니다.

## 15. 공식 개발기간 이전에 만든 것인가요? 지금 제출 가능한가요?

실제 구현 시작일은 **2026년 9월 26일**입니다. 공식 사이트의 개발기간은 9월 29일~10월 6일이므로 날짜를 바꾸거나 전부 공식 기간에 새로 만든 것처럼 표시하지 않습니다. 기존 구현의 제출 허용 범위와 참가 부문은 주최 측에 확인해야 합니다. 공식 페이지는 박사과정을 일반부에 포함한다고 명시합니다. 현재 문서는 준비 자료이며, 사전 개발물의 접수나 참가 자격이 승인되었다는 뜻이 아닙니다.

## 16. 남은 제출 준비와 평가 기준은 무엇인가요?

2026년 9월 26일 재확인한 공식 규칙에는 완료보고서 A4 5쪽 이내(표지 제외), 기술설명서 1쪽, 검증 가능한 소스코드 또는 저장소 정보, 시연영상 3분 이내, 발표자료 10장 이내의 다섯 종류가 명시되어 있습니다. 세부 양식과 FAQ는 9월 29일 안내를 확인해야 합니다. 공식 페이지는 작동하는 핵심 흐름과 Agent의 문제 해결 과정을 강조하지만, 공개되지 않은 세부 배점이나 우승 가능성을 수치로 만들지 않습니다.
