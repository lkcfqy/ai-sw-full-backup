## 1. 문제, 목표와 구현 범위

사진으로 전달된 부품 목록과 주문 수량을 대조할 때는 “무엇이 몇 개 보이는가”뿐 아니라 “어느 주문 버전을 확인했는가”도 중요하다. 주문이 변경되어도 이전 사진 검사 결과를 계속 사용하거나, 불확실한 사진을 확정된 수량처럼 기록하면 검토 근거가 맞지 않게 된다. KitGuard는 이 문제를 **사진·BOM 자료의 버전별 검토**로 정의한다. 현재 주문, 사진, AI 관찰, 차이와 검토 의견을 연결하고, 근거가 부족하면 추가 자료나 사람의 확인을 요청한다.

대상 사용자는 부품 사진과 수량표를 주고받는 소규모 조립·교육·자료 검토 담당자이다. 이는 도입 대상으로 설정한 가설이며, 실제 고객 확보나 현장 성과를 의미하지 않는다. 이번 구현은 공개 실사 사진으로 실행 가능한 디지털 검토 MVP이다.

**핵심 기능은 다섯 가지다.**

1. 현재 BOM과 사진 출처·검사 범위를 등록한다.
2. 로컬 시각언어모델로 물체 목록을 얻고, 프로그램이 수량과 주문 차이를 계산한다.
3. 불확실성에 따라 추가 자료 또는 수동 검토를 선택한다.
4. 주문 변경 시 이전 검사를 무효화하고, 새 버전에서 다시 검사한다.
5. 원래 AI 판단과 검토 의견을 보존하여 오프라인 증거 묶음으로 내보낸다.

현재 수량 범위는 bolt·nut·washer·bracket 네 가지 거친 분류, 분류별 0–3개, 총 1–12개이다. bolt는 형태가 다른 나사류를 합친 분류이다. 치수·재질·나사산·SKU 일치와 산업 안전 인증은 다루지 않는다. 선택 영역을 사용하는 경우 영역 밖은 검사 대상이 아니다.

**이번 결과의 구분:** v0.7은 공개 사진의 디지털 검토와 명시적 같은 사진 재사용을 추가했다. 실제 모델을 이용한 새 UI 흐름은 확인했지만, 그것이 새로운 정확도 평가나 사용자 연구는 아니다. 모델 성능의 과거 근거와 이번에 진행하는 새 사진 비교 평가는 4쪽에서 분리한다.

## 2. Agent 구조와 자체 개발 내용

```text
현재 주문·사진 → 로컬 모델 관찰 → 프로그램 수량/차이 계산
       ↑                                  ↓
새 버전·새 근거 ← 추가 자료 / 수동 검토 / 디지털 검토 기록
                                      ↓
                              이력·증거 묶음 내보내기
```

KitGuard는 **고정 규칙으로 실행을 관리하는 Agent**이다. 목표는 현재 버전과 근거에 맞는 수량 판단을 제공하는 것이다. 모델은 사진의 물체 분류·추정 위치·불확실성을 구조화하고, 프로그램은 실제 결과와 상태에 따라 다음 단계를 결정한다. 무제한 자율 계획이나 모델이 임의로 정하는 도구 체계를 주장하지 않는다.

| 구성 | 실제 역할 |
|---|---|
| 관찰 도구 | 원본과 90도 회전 사진의 물체 목록을 얻는다. 두 관찰이 명확하게 일치하고 nut/washer 후보가 있을 때 국소 분류·형태 확인을 실행한다. |
| 판단 | 목록에서 수량을 계산하고 BOM과 비교한다. 불확실하면 `null`을 유지하며 0이나 기대 수량으로 채우지 않는다. |
| 상태·피드백 | 주문 버전, 사진, 검사 범위와 근거 세대를 저장한다. 다른 추가 사진으로도 계속 불명확하면 정해진 예산 후 수동 검토로 넘긴다. |
| 디지털 검토 | 동의·추가 자료 필요·이견·판단 불가를 원래 AI 결과와 함께 보존한다. 공개 사진의 검토는 실물 완료 기록을 만들지 않는다. |
| 내보내기 | 사진, 버전별 결과, 출처, 모델/프로토콜, 검토 이력과 파일 해시를 JSON·ZIP·오프라인 화면으로 제공한다. |

**재사용한 기반:** Qwen3.6-27B의 MLX 커뮤니티 4-bit 양자화 모델, MLX-VLM 추론, FastAPI, SQLite와 일반 이미지 처리 라이브러리이다. 기반 모델을 자체 학습했다고 주장하지 않는다. 별도 연구용 검출기는 현재 주 판단에 사용하지 않는다.

**기존 구현과 신규분:** 프로젝트는 9/26에 시작했다. 기존 관찰·상태 엔진을 재사용하고 10/2에 공개 사진 검토·명시적 재사용·버전별 증거 UI/API와 독립 비교 도구를 추가했다. 선택적 확인 후보는 실험 전용이다. 기반·AI 코딩 도움은 별지2 신고 항목이며 사전 원형 사용의 주최 측 허용 여부는 아직 미확인이다. [기여 구분](CONTEST_PERIOD_CONTRIBUTIONS.md). 시각 관찰에 BOM 목표 수량을 주지 않는다.

동일 모델의 반복 관찰은 서로 독립적인 전문가 투표가 아니다. 공통 누락이나 같은 분류 오류는 남을 수 있다. 강화 절차는 알려진 수량을 불확실로 바꿀 수 있지만, 모델이 놓친 물체를 정답표로 보충하지 않는다. 구현 근거: [Agent 판단 코드](../../kitguard/app.py), [시각 관찰](../../kitguard/vision.py), [공개 사진 검토 계약](PUBLIC_REVIEW_API.md).

## 3. v0.7 실제 실행: 같은 사진, 다른 주문 버전

2026-10-02 한국시간, 공개 개발 예시 `bag-revision`으로 브라우저→FastAPI→실제 로컬 MLX 흐름을 실행했다. MVTec LOCO의 기존 개발 사진이며 새51 평가에 포함하지 않는다. 발표·편집 시연 영상도 이 실행을 사용한다.

| 단계 | 실제 요구·관찰·결과 |
|---|---|
| R1 최초 검사 | 요구 3/2/2/0, 관찰 2/2/2/0, `correct`(나사류 차이 -1). 기록된 관찰 소요 51,488ms. |
| R1 검토 기록 | `DEMO-AUTOMATION`이 `inconclusive`로 저장. 자동화 검수이며 실제 참여자 의견이 아니다. |
| 한국어 제안·R2 승인 | “볼트를 2개로 변경하고 나머지는 유지해 주세요.”라는 사전설정 시연 지시를 제안으로 해석하고 명시적 승인 뒤에 R2를 만들었다. 요구 2/2/2/0, R1 검사 무효·이력 보존. |
| 같은 사진 재등록 | 동일 픽셀을 공개 사진 재사용으로 명시했다. `physical_capture:false`, `requires_new_inference:true`. |
| R2 새 검사 | 관찰은 다시 2/2/2/0, `ready`(현재 사진 수량 일치). 기록된 관찰 소요 46,614ms. |
| 저장·내보내기 | R2 개발 검토를 별도로 저장하고 증거 ZIP을 내려받았다. 검사·검토는 해당 버전과 묶여 있다. |

수량 벡터의 순서는 bolt/nut/washer/bracket이다. `correct`는 프로그램의 “차이 조정 필요” 결정 이름이며 “정답으로 검증됨”이라는 뜻이 아니다. 위 시간은 검사 기록의 `latency_ms`이며 사람의 작업 시간이나 전체 업무 완료 시간은 아니다. 두 값만으로 일반적인 속도 개선을 주장하지 않는다.

**확인한 동작:** 같은 사진이어도 주문 버전이 다르면 별도 검사를 요구한다. R1은 과거 이력, R2는 현재 근거로 표시된다. 두 검사·두 검토·한 재사용·실물 완료0건과 ZIP 내 네 파일의 해시/바이트 수를 확인했다. 15개 실제 화면을 보존했으며 영상의 기다림·조작 구간은 압축한 편집 시연으로 표시한다.

**이 실행의 한계:** 실제 업무의 BOM 변경은 실제 요구 변경을 확인한 사용자가 승인해야 한다. 수량 일치를 위해 요구를 낮추는 것은 부족 문제의 해결이 아니며 요구3의 차이 -1은 역사에 남는다. 이번 두 검토는 자동화 Agent가 입력했으며 `physical_completion:false`, `user_validation:false`이다. 실제 사용자 평가·부품 보충·새 촬영·출고를 검증하지 않았다.

원시 근거: [시연 주문 JSON](../../test-results/browser/public-review-v07/demonstration/order.json), [실행·ZIP·화면 검증](../../test-results/browser/public-review-v07/demonstration/verification.json), [개발 기록](CONTINUATION_20261002.md). 앞선 `mixed-screws`의 24.092/22.078초 실행은 별도 역사 기록이며 이 시연 시간에 합산하지 않는다.

## 4. 정량 평가: 과거 근거와 이번 평가를 분리

**측정 정의:** C는 네 분류의 수량이 모두 맞고 실행 가능한 관찰, W는 명확하지만 수량이 틀린 관찰, U는 불확실·추가 자료 필요, E는 실행/출력 실패, N은 계획했으나 미실행인 사진이다. 결과가 맞아도 불확실 표시가 있으면 C로 세지 않는다. 실패와 미실행을 분모에서 빼지 않는다.

## 5. 활용 가설, 데이터 책임과 재현

### 활용과 사업화 가설

초기 도입 형태는 **기존 사진과 BOM을 가진 소규모 팀의 로컬 자료 검토 도구**이다. 사용자는 반복 수량 확인과 주문 변경 검토를 수행하고, 관리자에게 사진·버전·판단 근거가 묶인 기록을 전달한다. 향후 고객이 적법하게 보유한 사진을 사용하며, 필요한 BOM 형식 연동과 보관 정책을 함께 정한다.

사업 모델 후보는 팀 단위 소프트웨어 이용·유지보수와 초기 설치/BOM 연동 지원이다. 아직 유료 고객, 계약, 매출 또는 가격 수용도 조사는 없다. 도입 의사결정은 실제 사용자의 전체 검토 시간, 잘못된 확정, 재검토 건수와 기록 재확인 가능성을 측정한 뒤 내려야 한다. 이번의 기계 관찰 시간이나 정적 공개 사진 점수로 인건비 절감률·ROI를 산출하지 않는다.

### 데이터와 사용 책임

MVTec [LOCO AD](https://www.mvtec.com/research-teaching/datasets/mvtec-loco-ad)와 [Screws](https://www.mvtec.com/research-teaching/datasets/mvtec-screws)의 공개 실사 자료를 사용했다. 데이터 조건은 CC BY-NC-SA 4.0이며 출처, 원본 해시와 파생 영역을 기록한다. 공개 데이터의 비상업 조건을 향후 제품의 고객 데이터 사용권과 혼동하지 않는다. 기반 모델의 라이선스도 데이터 허가를 대신하지 않는다. [데이터 출처 기록](../DATA_PROVENANCE.md), [모델·데이터 재현 검토](../MODEL_DATA_REPRODUCIBILITY_REVIEW.md).

정상 추론은 로컬 MLX에서 실행되고 사진을 클라우드 모델로 보내지 않는다. 현재는 `127.0.0.1`의 단일 사용자 도구이며, 사용자 계정 인증이나 조직별 접근 제어는 제공하지 않는다. 검토자 코드는 자가 입력이고 파일 해시는 무결성 확인 수단이지 서명·신원 또는 실제 촬영 인증이 아니다. 실제 사용자의 피드백 가산점이나 현장 검증 실적은 본 보고서에서 주장하지 않는다.

### 실행과 재현

실제 검증 환경은 Apple M5 Pro/64GB, Python 3.12이다. 모델은 `mlx-community/Qwen3.6-27B-4bit`, revision `c000ac2c2057d94be3fa931000c31723aac53282`, 주 이미지 최대변1536, 기본 `spatial_guarded`이다. 이미 설정된 환경에서는 `bash scripts/run.sh`로 시작한다. 최초 설치·모델 확보 절차는 최종 소스 패키지 안내에 포함하고 모델 가중치 자체는 패키지에 복제하지 않는다. 다른 하드웨어에서의 속도나 무설정 실행은 검증하지 않았다.

공학 테스트는 API 계약과 상태 보호를 확인하며 모델 정확도와 구분한다. 출처 선택, 코드/프로토콜, 실제 입력·원시 출력, 오류와 시간이 평가 기록에 남는다. 프로젝트 개발 시작일은 2026-09-26이고 v0.7 추가 개발 기록은 2026-10-02부터이다. 기존 개발분과 이번 추가 구현을 섞어 개발 기간을 바꾸어 표시하지 않는다.
