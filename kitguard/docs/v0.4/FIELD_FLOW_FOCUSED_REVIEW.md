复核范围是 fresh 工单/照片交接、韩中数量输入、人工阶段失败/刷新恢复、busy 错误，以及返回决策的用户解释。没有重复此前 74 条完整流程，没有调用 GPU 或使用任何新的真实模型样本。

## 找到并修复的具体问题

**P2：AI 决策 `manual` 与人工方法名使用同一翻译键，显示成“01 人工 / 01 수기”。**

后端 `action.kind=manual` 可以直接形成 `check.decision=manual`，并不要求先尝试两次补拍。记录台的最终 AI 卡片和读取已有 check 的恢复分支把此决策送入 `t('manual')`；该键原本是人工方法的编号标题，导致不确定观察被显示成阶段名称，用户看不到“需要人工复核”。

隔离端口 8789、显式 FakeAnalyzer 的实际 API 反例已确认：服务保存 `decision=manual`，韩文 AI 卡片显示“01 수기”，中文显示“01 人工”。图片是标注为工程用途的合成文字图，不是真实模型测评。复现记录在 `test-results/browser/field-study-flow-review-v04/result.json`，旧 JS 字节保存在 `before-study.js`，两种语言缺陷截图也已保存。

修复只改 `kitguard/static/study.js`：新增决策专用翻译函数，把 API `manual` 映射到已经存在的 `manual_review` 文案。人工方法名仍保持“01 人工 / 01 수기”；其他决策的现有解释不变。最终卡片和读取已有结果分支都使用此函数。

修复后真实 Chrome 的 **14 条定向检查通过**：两种语言均正确显示“需要人工复核 / 수동 확인 필요”，人工方法标题不变，恢复分支仍仅提供绑定已有结果，320px 无溢出，零 JS 错误、零修改请求。恢复分支为浏览器 DOM 内的视图构造，使用实际保存的 check；没有修改已闭合服务端试次或伪称一次真实恢复执行。

## 其余流程的结论

- 主工作台先建新工单并上传当前版本照片，再返回记录台重新读取，可以得到可登记对象。已尝试核验、已有检查、照片版本过时的工单会被前端过滤或服务端拒绝；直接在主工作台提前点击核验会失去该照片作为首次对照的资格，这是协议约束。记录台入口与空列表提示提供重新读取与新工单路径。
- 数量字段为必填数字输入，前端再检查 0–100 整数；服务端使用 StrictInt。此前韩中切换、双次数量不一致、人工输入与刷新恢复已在实际 Chrome 完整流程覆盖。未发现会把空白/小数/负值悄悄当作有效数量的路径，不重复制造同类测试。
- 人工失败/放弃是终态，分母保留；未结束的人工试次刷新后仍可完成，已终结的试次不能重写。服务器重启的未知用时保留为 null；相关 API 已有独立反例测试。
- 新健康接口返回 `inference.busy`，运行层忙碌时拒绝新请求且队列容量为 0。前端保留后端双语“等待上一任务结束”说明，没有自动重试。当前记录台不主动轮询 busy；一次已开始的 AI 试次若收到忙碌拒绝，会按一次执行失败保留，这与既定分母规则一致。

此轮只修复一个已重现的展示问题；未发现需要修改冻结后端或视觉方法的另一个关键断点。
