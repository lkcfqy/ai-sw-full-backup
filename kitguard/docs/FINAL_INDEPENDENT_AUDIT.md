## 3. 问题跟踪与准确表述要求

### O1：第二方向失败后的诊断信息不完整（已修复并关闭）

原问题是第二方向失败后，成功的第一观察只留在局部变量中。2026-09-26 根任务修复了 `_observe` 包装层：建立本次观察尝试记录，按实际完成的方向追加经过结构校验的观察、处理后输入 SHA-256 与运行信息；异常对象携带诊断的深拷贝，包括状态、模式、模型名、原始输入 SHA-256 与异常类型。benchmark 在错误行另存 `error_diagnostics`，仍将成功运行字段 `runtime` 置空。API 从当前异常读取诊断，`store.fail_inspection` 仅在当前 token 匹配时，将其写入该订单的 `inspection_failed` 事件。

独立复查运行了现有 9 项 orientation CPU 测试；另用实际 `LocalVision` 适配器（只替换生成函数）、实际 API 和 SQLite，连续注入第二方向解析失败、第二方向运行失败、下一订单第一方向失败。三个响应均为 503，订单没有检查记录、`latest_check` 为 null、状态为 `needs_action`；前两次保留正确首轮观察、输入散列与本次运行编号，第三次 passes 为空，没有借用上一请求数据；再次读取前三个订单时诊断保持隔离。机器记录及所测源码 SHA-256 在 `test-results/audit/failure_trace_recheck.json`。

该修复不补造失败方向的观察，`passes` 只列实际成功并通过校验的方向。超时/取消仍走独立失败分支，不声称后台模型计算已经停止。未来可以进一步增加明确的失败阶段、失败方向输入散列，但不影响本项“保留真实首轮且不串请求”的关闭。修复不追溯重写前述历史运行的快照或原始记录。**独立审计未修改核心代码。**

### O2：app-upload 的范围与计时不能称为完整产品端到端（报告口径必须处理）

runner 使用临时 FastAPI 应用、隔离数据库及真实上传路由产生 JPEG，再直接调用 `vision.observe`。它没有调用实际 `/inspect` 或 `/complete` 路由，不覆盖完成确认、并发核验、界面操作或人的补证时间。

计时起点在临时应用、数据库和上传归一化之前，因此包含这些步骤以及输入保存/散列和视觉观察。表中时延应称“该离线 app-upload 基准每行耗时”，既不是纯模型解码时间，也不是使用者完整核验时长。此外，直接观察路径没有 `/inspect` 的 300 秒超时保护；普通异常会记账，永久阻塞可能使运行未完成。只接纳 `status=completed` 且行数齐全的正式结果。

### O3：源码快照存在可加固的时序窗口（未来复现加固）

runner 先导入模块，再复制源码快照并读取工作区文件计算散列。若在导入、复制和散列之间修改源码，理论上可能出现“已加载模块”和“保存源码”版本不一致。当前审计的两轮快照散列全部一致，且运行前后检测没有变化；没有证据表明这两轮受影响。

后续可从同一已冻结字节生成快照与散列，并在独立进程中从该冻结工作树执行，或在运行前锁定提交并拒绝工作区变化。不得因未来加固建议就宣称当前数字无效。

### O4：order eligibility 指标名称需要保持清晰（当前两轮不受影响）

当前 `score_case` 把名义订单追加到任务列表后，以是否存在任一任务设置 `in_product_scope` / order eligible。若将来某个真值超出每类数量上限，但具有有效名义订单，它可能被记为 eligible，尽管无法构造“与真值匹配”的范围内订单。

建议拆分“真值符合产品范围、可生成匹配/不匹配订单”与“存在有效名义订单任务”两个计数，或更名。当前 LOCO 开发集真值都符合范围；Screws 清单没有名义订单且全部超出单类 3 个的范围，因此本轮数字不受影响。Screws 只能作为计数压力测试，不能据其结果报告范围内订单任务成功率。

### 真值来源与错误后果

作者论文 *Beyond Dents and Scratches: Logical Constraints in Unsupervised Anomaly Detection and Localization*（IJCV 2022），本地 `datasets/provenance/mvtec_loco/original_paper.pdf`，PDF 第 5 页 §3.1，明确正常袋含 two washers、two nuts、one long screw、one short screw。原文短句：“A screw bag contains exactly two washers, two nuts, one long screw, and one short screw.” 官方来源：https://link.springer.com/article/10.1007/s11263-022-01578-9 。论文 SHA-256：`3db889a0f0a7db755f2d10d55ed5cfa256e9624b3ed7971e9723fb2f3a4185c6`。

本项目把 long/short screw 合并为 bolt，所以正常粗分类为 (bolt,nut,washer,bracket)=(2,2,2,0)。这不评估长短规格错误，也没有 bracket 阳性。异常真值只由作者单一数量缺陷编码增减推导；没有把掩码面积、连通区域或本助手视觉判断当作新的人类实例标注。

1. **正常图 `test/good/113.png`**：真值 (2,2,2,0)，模型 (2,4,2,0)。本次审阅所用原图 SHA-256 为 `a637d04393b7ddbd620d80ba86c3eb37b7ea4d4df2c4f43bc5e765531fc7d8ba`。本助手查看原图及模型点位后，认为额外两个 nut 点位很可能落在 bolt 头部；这是错误原因的视觉解释，不是新增人工实例真值。对标准/真值匹配订单，规则输出 correct，建议错误地移除 2 个 nut；若盲从，可能把合格套件变成缺件。对固定扰动订单 (3,2,2,0)，补 1 个 bolt 与订单一致，但同时移除 2 个 nut 仍错误。本图没有在这些测试订单上得到 false-ready。
2. **异常图 `test/logical_anomalies/042.png`**：真值 (3,2,2,0)，模型 (2,2,2,0)。原图 SHA-256 为 `b09fc8b770c8db05f40857565792a5ba7c00c8420a6fb7ed0aa18bc459fe9613`。作者掩码 `ground_truth/logical_anomalies/042/000.png` 经独立核查只有像素值 [0,251]，SHA-256 为 `ceb08093f757950b22bc52da7e196d99a64ecd4296fc0d6978b4ce784c43f1db`；`defects_config.json` 把 251 定义为 `1_additional_long_screw`（配置 SHA-256 `99d2f93ac25f632d594ec0e4e610d30c157b8f4985cd3bd76828375103bdaacd`）。因此正常 2 根加 1 根得到 bolt=3。本助手观察原图可见重叠螺栓，模型只列两根。标准订单 (2,2,2,0) 得到错误 ready，忽略多出的一根；真值匹配订单 (3,2,2,0) 则错误地建议再加一根。

**042 的“名义订单 false-ready 1/24”和“固定扰动 false-ready 1/48”对应同一张图片、同一个 (2,2,2,0) 订单，不能称为两个独立错误放行。** 所有决策均是离线规则重放，基准没有调用 `/complete`，没有实体补件或真实出库。应用中还要求人的明确确认；但这不应掩盖模型已产生错误 ready 提示的事实。
