# KitGuard：核验记录追溯界面

更新时间：2026-09-26。此文档描述产品实现与工程验证，不是实物识别准确率或竞赛评测成绩。

## 本次实现

保留韩语默认、中文切换和现有响应式工作台。在“操作历史”中增加两个视图：

- **核验记录**：列出服务器返回的每次 `check`，包括当时版本、结果、日期、耗时、对应照片和当前可用性。尚无核验时展示空态，不补造历史样例。
- **操作事件**：显示实际事件；存在关联 `check_id` 时可以打开详情。失败事件有已保存的 `payload.reason` 时可展开查看原因。

点击记录打开只读详情。每次打开或刷新都会通过 `GET /api/orders/{id}` 读取新快照，详情显示查询时间。快照保存在独立前端状态中，不覆盖可能正在运行的当前工作台任务。

详情包含：

1. 当时核验结论与查询时的当前版本，明确区分历史结果和当前能否继续使用。
2. 当时需求、观察和差异。需求优先取该检查自身的 `requirements_snapshot`，其次取相同 `revision` 的版本快照，最后取该次检查保存的 `differences.required`。全部缺失就显示未知，绝不用当前订单代替。
3. 该检查的 `photo_id` 对应照片、模型保存的关注区域、照片元数据与文件哈希。哈希只作为保存文件标识，不声称能够证明真实拍摄时间或同一物件。
4. 保存的操作建议、问题、模型、后端、处理耗时、证据版本、服务器有效标记和检查 ID。
5. 与此检查实际关联的人工完成回执。后续订单变更不会隐藏旧回执，也不会把旧回执解释为新版工单已完成。
6. 输入与执行事件、后续影响该记录的事件，以及完整原始 JSON 下载入口。

详情只有读取、图片查看、下载和关闭功能；没有完成工单、批准改版或重新应用历史结果的入口。`backend: test` 的检查保留显著工程测试标记。

## 有效性与解释边界

当前可用性同时检查服务器 `valid` 标记、订单版本、最新检查 ID、最新实物照片、已知且一致的 `evidence_epoch`、是否存在进行中的核验，并排除测试后端。`valid: true` 不单独等于可以完成订单，实际完成仍由现有后端接口校验。

后端没有为每次检查单独保存完整的 `invalidation_reason`。界面因此使用版本、照片关系及后续事件解释改版、换照片、换参考图、重新核验造成的失效，并明确标注为**根据记录关系生成的说明，不是另存的模型推理内容**。可识别原因不足时显示“服务器已标记失效，无法确定更具体原因”，不猜测。

事件关联优先用 `check_id`、`photo_id`、`revision` 和数组中的已存事件顺序。若缺少检查保存事件，才以时间过滤可关联事件。新增的程序步骤与历史参考图片分别来自后端实际保存的 `tool_trace` 和 `reference_ids`；未保存的步骤、视觉置信度或参考关联不会由前端补造。

如果保存的版本需求与差异项、观察或差值互相矛盾，详情显示数据不一致提示，要求核对 JSON，不静默掩盖。

## 改动文件

## 补证反馈与实际执行步骤

详情现已接入后端可选字段，保持旧记录兼容：

- **补证反馈**：读取 `evidence_feedback`，按本次检查的历史版本标注，展示保存的结果、双语说明、前后照片、已解决/仍不明确/仍有数量差异的零件，以及 `observed_changes` 中的原观察→新观察。`null` 和旧记录未保存字段分别说明；空数组显示“无”，缺失数组不推断为空。
- **物理操作边界**：每个有反馈的记录固定显示“仅比较两次图像观察，不能证明实际物料操作”。观察相符不等于证明操作者确实补料、移动了同一批物件，反馈不会生成完成按钮。
- **关联前次核验**：仅在真实 `previous_check_id` 存在时提供只读入口，继续通过 GET 获取独立详情快照。
- **实际执行步骤**：按保存顺序展示 `tool_trace`，包括图像观察、当时数量比对、先前证据比较、动作选择、提交前版本/证据复核。`not_applicable` 明确显示“不适用”，不改称成功。步骤可展开查看保存字段；缺字段时显示未记录，不画假流程。
- **观察关注信息**：有 `observation_context` 时可展开查看上次不明确部件和操作类型，明确该字段不保证模型实际利用了信息。
- **当时参考图**：仅以检查自身的 `reference_ids`，在已存 `reference_history` 等记录中寻找同 ID 图片；即使当前参考图已换，也不会替换旧关联。旧检查没有参考 ID 时说明未记录。
- **检查输入快照**：优先采用 `requirements_snapshot`；与同版本需求或保存差异不一致时提示异常。图片哈希优先采用 `photo_sha256`，与照片记录哈希冲突时提示核查原始 JSON。

程序执行记录只是保存的程序调用步骤，不是模型内部推理内容。补证反馈中的历史“数量相符”不会被解释成新版订单仍然满足要求。

### 同一模型双方向观察的历史展示

`check.observation_verification` 存在时，历史详情增加两次观察的数量表、原始方向/逆时针 90° 标签、各自输入哈希、问题及动作；显示服务器保存的 `counts_agree` 与 `clear_agreement`，不自行把某个 pass 代替最终观察。缺失或 null 的旧字段不会生成虚构观察；未知字段值会转义后展示。`compare_orientation_observations` 在中韩文实际执行步骤中有对应名称。

界面明确说明：两次调用来自相同模型且具有相关性，不是独立专家、概率或准确性保证；旋转图像不是新拍摄的实物证据。该区块只有读取能力，不增加完成订单、重用旧核验等操作。

真实 Chrome 在 `127.0.0.1:8769` 的独立工程 API 上验证，结果与截图位于 `test-results/browser/orientation-details/`。该服务注入有明确 `backend:test` 标记的双观察夹具，原始图片也标为 SYNTHETIC；没有加载模型或访问生产数据库。25 项断言通过，包括保存的 1/2 差异、最终 null 不被替代、旧版本数量、中韩翻译、旧记录兼容、HTML 转义、手机无溢出及全程无 POST；没有 JavaScript 错误。为调整截图滚动位置进行的同组复检不增加断言样本数。韩语桌面截图可用于解释工程界面，不能用作真实识别成绩。


### 可选物体清单与估计位置

`spatial.js` 仅读取可选的 `check.object_evidence`：协议必须为 `spatial_inventory_v1`、坐标框架必须为 `normalized_original`，物体清单最多 20 项，每项保存四类之一及 `[0,1]` 的两个数值坐标；不接受字符串、布尔值、非有限数或越界坐标。未知协议、错误列表和旧记录缺失字段均不显示空面板。该字段已由选定的单次空间清单协议采用；旧记录继续兼容。

历史详情以该核验实际关联的照片显示编号点与只读清单。工作台只选择与当前显示照片 `photo_id` 相符的已存核验；两处若同时保存了图片 SHA 且不一致，则不画点。保存的版本号始终显示，旧版观察不改变当前订单可完成状态。每次切图、切检查或重新渲染都默认隐藏点位，避免将上一次观察沿用到另一张图。原有问题区域保留在编号层之上。

按钮可由 Tab 聚焦、Space / Enter 切换，使用 `aria-pressed` 和 `aria-controls`；物体清单通过原生 details 展开。编号只是保存列表的顺序，界面明确说明不是托盘编号。中韩文本注明位置是模型估计，数量由程序从列表计算，仍可能重复、遗漏或分类错误，不能证明实物状态或实际物料操作。测试记录在按钮旁显式标为工程测试。所有外来文本经转义，位置只能使用校验后的数值。

`test-results/browser/spatial-evidence/` 保存只读合成 HTTP 夹具、浏览器脚本、结果与四张桌面/手机截图。它使用手工指定的测试列表和既有 SYNTHETIC 图片，未读取或冒充任何真实空间探针结果，也没有加载模型、改动核心 Python 或写入生产数据库。真实 Chrome 的 36 项断言通过，覆盖照片/哈希绑定、键盘切换、切图复位、坏字段拒绝、HTML 转义、问题区域层级、旧记录兼容、韩中展示、390px 手机无溢出，以及 1440×900 下核验入口可见；没有 JavaScript 错误或写入请求。补充布局断言是同组复检，不是新增模型样本、用户研究或定位准确率。

选定协议集成后，实际步骤 `derive_counts_from_object_list` 已增加韩中名称，保存的 `listed_objects` 与 `uncertain_parts` 可在步骤字段中展开查看。Node 语法检查和两种语言的实际翻译函数检查均通过；未改变历史有效性或完成逻辑。
