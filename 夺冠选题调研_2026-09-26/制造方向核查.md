# 制造方向选题核查

核查日期：2026-09-26（韩国时间）。本文是选题研究和实验设计，没有开发比赛代码，没有取得实验成绩。官方评审细则和竞争对手作品尚不完整，因此不能保证第一名。

## 主选：PCB 质量异常复核与处置 Agent

建议题目：**证据驱动的 PCB 质量异常复核与处置 Agent**。韩文工作标题：**증거 기반 PCB 품질 이상 검토·조치 AI Agent**。

把 MVP 限定为一种 PCB、一个检验工位、四项核心功能：异常证据呈现；SOP 检索与缺失信息补问；处置工单草稿及人工确认；复检证据校验与关单。完整流程如下：

> 图像和工件标识输入 → 固定检测器定位异常 → Agent 检索适用 SOP 并引用具体条款 → 对缺失、模糊或矛盾的信息补问 → 生成处置工单草稿 → 人工确认 → 在本地演示系统建立工单 → 收到复检证据 → 校验复检是否对应同一工件、是否满足关闭条件 → 关单或继续请求证据 → 回读状态并留下审计记录。

判断存在不确定性时，应输出“需要复核”，而不是自动把未识别的工件判为合格。现场演示至少包括一个顺利闭环案例，以及一个因图片模糊、工件信息缺失或 SOP 条款冲突而请求补充证据的案例。

不要加入剩余寿命预测、制造根因因果判断和排程功能。图片缺陷定位不能直接证明故障根因；跨多个工序会稀释八天内的验证深度。

## 数据、基线与可得性

### Amazon VisA：优先数据来源

- 作者仓库：https://github.com/amazon-science/spot-diff
- AWS 官方目录：https://registry.opendata.aws/visa/
- 作者提供的数据直链：https://amazon-visual-anomaly.s3.us-west-2.amazonaws.com/VisA_20220922.tar
- 证据：包含 10,821 张图像，其中 9,621 张正常、1,200 张异常；12 个对象子集，包含四种 PCB；提供图像级及像素级标注、官方数据划分。数据许可证为 **CC BY 4.0**，与仓库代码的 Apache 2.0 许可证分开。
- 可得性：AWS 官方目录明确无需 AWS 账号。2026-09-26 使用 `curl -sSIL --max-time 25` 检查上述作者直链，返回 HTTP 200、`Content-Type: application/x-tar`、`Content-Length: 1929840640`，约 1.93 GB。**只检查响应头，没有下载数据，也没有核验全部样本内容。**
- 应用范围：先选一种 PCB，保留作者原始训练/测试划分。论文数据只证明图像检测性能，不能证明昌原工厂的实际生产效果。

### 成熟检测基线

- PatchCore 作者实现：https://github.com/amazon-science/patchcore-inspection
- Anomalib 官方仓库：https://github.com/open-edge-platform/anomalib
- 证据：PatchCore 提供公开异常检测实现；Anomalib 提供现成异常检测算法及训练、推理、基准工具，支持 CPU 后端，仓库为 Apache 2.0。
- 边界：尚未安装或在用户设备上运行，不承诺 CPU 推理延迟或训练时间；比赛开始后的第一天必须测量。若采用预训练权重，应单独记录权重来源及许可证。不能把现有检测算法的精度当成本项目原创贡献。

### 为什么不优先 MVTec AD / AD2

- MVTec AD：https://www.mvtec.com/research-teaching/datasets/mvtec-ad
- MVTec AD2：https://www.mvtec.com/research-teaching/datasets/mvtec-ad-2

## 真实性与原创性边界

VisA 没有用户工厂的真实 SOP、批次关系、维修工单或复检闭环。自建工件 ID、流程状态、SOP 和工单必须明确标注为**演示/仿真数据**，不能以真实工业部署展示。自行编写的 SOP 应称“原型检验流程”，不能暗示满足某个未验证的工业标准。公开数据中重新选择另一张正常图片，也不能谎称是原缺陷工件维修后的真实复检图。

若没有真实工厂数据，这个项目的实证主张应限于：公开图像测试集上的检测性能、定义清楚的流程案例中的任务完成情况、参与者测试中的操作时间与错误。不能宣称减少了工厂报废率、停机时间或成本。

无工厂伙伴时，原创性和实践证据确实较弱。可采用两种有限增强方式：

1. 找有相关经验的实验室或制造人员审查演示 SOP 和案例，记录其角色、人数、审查方式与意见。专家审查不等于工厂试点。
2. 在正式开发窗口内，用允许拍摄的教学/实验对象收集一小组真实复检过程。必须明确它是实验室验证，且与公开 PCB 测试集分开报告；不要把不同物体或不同拍摄条件直接混成统一准确率。

### 现有商业能力：不能把 RAG + 工单说成首创

- Siemens Maintenance Copilot 官方说明：https://help.assetmanagement.siemens.com/help/Content/Documentation/Maintenance/Asset%20Essentials/EnterpriseFeatures/AI-Driven%20Capabilities/Maintenance%20Copilot.htm
- Siemens 维护 Copilot 发布说明：https://press.siemens.com/global/en/pressrelease/siemens-expands-industrial-copilot-new-generative-ai-powered-maintenance-offering
- IBM Maximo 官方产品：https://www.ibm.com/products/maximo
- IBM 官方研究介绍：https://research.ibm.com/blog/Maximo-automating-asset-management
- 核查结果：Siemens 已能依据资产手册和维护记录提供带来源的诊断及备件建议；IBM Maximo 已覆盖维护计划、排程、设备状态与工单。因此，单纯“手册问答＋自动生成工单”缺乏新颖性依据。

本项目可以争取的差异是：针对一个明确场景，**用可追溯证据决定下一步；信息不足时主动补问；把复检证据和工单状态关联；独立验证动作是否真正完成**。这是需要实验支持的实现贡献，不是全球首创声明。

## 怎样公平证明 Agent 带来增益

不要只与一个没有工具的聊天机器人比较，也不要给 Agent 更强检测器或更多信息。至少设置以下对照：

| 方案 | 相同条件 | 差异 |
|---|---|---|
| A：固定规则工作流 | 同一检测器、同一阈值、同一 SOP、同一输入与工具、同一人工确认环节 | 预先写好的分支和表单规则 |
| B：LLM + 工具 | 与 A 相同的数据和工具 | 由 LLM 决定下一步，不增加独立证据校验 |
| C：证据驱动 Agent | 与 A/B 相同的数据和工具 | 动态补问、来源核对、动作前后条件和状态回读 |

Agent 的检测器应完全固定，不能把 C 的检测更准解释成流程智能。A 应是合理且尽力实现的规则基线，包含明显的缺项检查和确认步骤，而不是刻意弱化的稻草人。三者都可在相同规则下补问，也都必须遵守相同人工确认机制。

在开发完成前锁定测试案例及参考答案，建议 30–50 个原型流程案例，正常、异常、缺失字段、图片模糊、SOP 版本矛盾、工具失败、重复事件、复检工件不匹配均应覆盖。开发集与最终测试集分开，另留至少一组此前未用过的表述或案例组合。场景及标注方法应随复现包提供；数量是建议目标，不是已经完成。

报告两层指标，避免混淆：

- **视觉层**：缺陷漏检率、正常样本误报率、检测延迟；保留作者测试集，阈值仅用训练/验证信息确定。
- **流程层**：正确下一步比例、错误关闭/错误放行次数、成功闭环比例、不必要补问次数、人工操作时间、总时延和每例调用成本。流程成功必须同时满足正确判断、正确工单状态、有效复检证据；不能只看工具有没有返回成功。

若请少量人员测试，使用相同难度的案例并平衡使用顺序，报告人数、经验和分布，不把 2–3 人的原型测试泛化为行业效果。测试中若固定规则更稳、更快，应如实报告，收缩 Agent 的职责到规则难覆盖的信息整理和补问；不能预设 Agent 一定优胜。

## 八天范围

以下属于计划，不是开发成果；正式开发遵守赛事窗口。

- 第 1–2 天：一种 PCB 数据划分、固定检测基线、演示 SOP、案例定义、工具接口和本地工单状态。
- 第 3–4 天：SOP 引用、缺项补问、工单草稿、人工确认、复检关闭的端到端流程。
- 第 5 天：模糊证据、版本矛盾、重复事件、工具失败、工件不匹配等分支及审计。
- 第 6 天：固定规则对照、Agent 对照及有限人员测试；报告负面案例。
- 第 7–8 天：修复、复现说明、三分钟演示、报告与提交材料。

## 有真实数据时的备选：停机后的交期恢复 Agent

只有能取得真实订单、设备限制及生产人员反馈时才考虑替换主选，不与 PCB 主选合并。范围可为三台设备、十至二十张工单、一次停机事件：读取事件 → 获取缺失约束 → 求解重排 → 独立验证工序和设备限制 → 展示交期影响 → 人工批准 → 更新并回读排程。

基线来源：https://developers.google.com/optimization/scheduling/job_shop

Google OR-Tools 官方示例已有工序先后和设备不重叠约束。新增贡献应是获取和核实业务约束、解释不可行原因及事件后的执行验证，不能把调用求解器称为算法创新。如果只有自建仿真订单，只能报告仿真延期、违规及计算时间；不能声称真实工厂收益。

## 尚未验证的事项

- 用户是否有工厂伙伴、领域专家、适用的真实 SOP 或允许使用的工件图像。
- 用户实际计算资源和检测推理速度。
- VisA 下载后完整性、样本适配情况及最终采用子集。
- Agent 对固定规则的实际增益；所有效果数字都必须等实验后填写。
- 赛事详细评审权重，以及工业演示或使用公开数据对获奖的实际影响。
